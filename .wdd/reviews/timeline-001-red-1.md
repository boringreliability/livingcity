## BLOCKER
### B1. Test 10 fails a correct implementation: `seek(1500)` is outside the window that its own budget leaves (`timeline_001_snapshots.rs:322-326`)
- Measured on three_bridges 2026/7:
  - one snapshot is 37.9 KB at tick 600, and later snapshots are 41.3–42.5 KB;
  - with the budget at 4 × 37,906 B, the store holds 3 snapshots, `[2160, 2280, 2400]`, so `window_start = 2160`;
  - `tl.seek(1500).unwrap()` panics.
- This does not depend on the bytes accounting. Snapshot sizes are flat after about 10 sim min, so 4 × one always leaves about 3–4 snapshots, which puts `window_start` at about 2040 or later.
- The test also never compares the state after a seek that happens after eviction, whether to the window start or to the middle of the window. This is the normal case in the browser (48 MiB ≈ 2 sim hours).
- **Fix** (verified: `p10_fixed` passes the correct implementation):
  ```rust
  let r = reference(world(&c.scenario, &[]), 2400);
  // … build tl, step 2400, start > 0 as now …
  let mid = start + 37;
  tl.seek(mid).unwrap();
  assert_eq!(observe(tl.world()), r[mid as usize], "seek inside the window after eviction");
  let before = (tl.world().state_hash(), tl.position_tick(), tl.head_tick(), tl.snapshot_ticks());
  // … the refusal loop unchanged …
  tl.seek(start).unwrap();
  assert_eq!(observe(tl.world()), r[start as usize], "seek to the window start after eviction");
  ```

### B2. No test restores a snapshot that holds non-empty reroute queues; a snapshot that drops the queues and flags passes all 14 tests
- T1 § Determinism explicitly requires "the reroute queues and flags". In the suite, though, the queues are empty at every snapshot tick:
  - With the 1800 closure in River City, the queues are `(0,0)` at tick 1800, `(25,7)` at 1801, and `(0,0)` again from 1802 (`probe3`). So test 3's "1801…1840 where the reroute queues are busy" holds only for 1801, and that state is regenerated by the replay, never restored.
  - In three_bridges, closures never exceed the 200/tick budget, so its queues are always drained within the tick.
- **Result:** the `drop_queues` mutant passes every frozen test. It restores with empty `priority_queue` / `periodic_queue` and clears `in_priority` / `in_periodic`.
  - That is exactly the mistake an implementer makes by classifying the queues as "transient, like the router".
- **Fix:** add a test (release-only is fine, see m1) where the closure lands one tick before a snapshot. River City has a 31 + 6 backlog at snapshot 1920.
  ```rust
  #[test]
  fn reroute_backlog_survives_restore() {
      let (s, main) = river();
      let cmds = [close(main[0], 1919), close(main[1], 1919)];
      let mut rw = world(&s, &cmds);
      let mut r = vec![];
      for _ in 0..=2100 { r.push((rw.state_hash(), rw.reroute_stats())); rw.step(); }
      // precondition: the budget ran out in step 1919, so snapshot 1920 holds a reroute backlog
      assert_eq!(r[1920].1.max_budgeted_in_a_tick, sim_core::params::REROUTE_BUDGET_PER_TICK);
      assert!(r[1921].1.switches_total > r[1920].1.switches_total, "precondition: backlog drained in step 1920");
      let mut tl = Timeline::new(world(&s, &cmds), UNLIMITED);
      tl.step_n(2100);
      for t in [1920u64, 1921, 1927, 2039] {
          tl.seek(t).unwrap();
          assert_eq!(tl.world().state_hash(), r[t as usize].0, "seek({t})");
      }
  }
  ```
  Verified: it passes the correct implementation, the `drop_queues` mutant fails it at `seek(1920)`, and the precondition is true (switches go from 200 to 231 in step 1920).

## MAJOR
### M1. Test 12 never seeks or checks snapshots after the edit, so three realistic bugs pass (`timeline_001_snapshots.rs:357-385`)
- **`snap_cmdlog` passes.** T1 says a `Snapshot` keeps "the full `command_log`".
  - An implementation that restores that stored log brings back the pre-edit log on a seek to ≤ 1200. That log has `open@2000` and lacks `close north@1200`.
  - Test 12 never seeks after the edit, so this passes.
- **`no_snap_after_edit` passes.** No snapshots are taken in 1320…2400. Seeks would silently replay up to 1,200 ticks, and the window would show stale data.
- **`truncate_after_check` passes.** `schedule(cmd.tick < position)` at `position < head` cuts the future and *then* returns `InPast`. One mistaken click in timeline-003 would destroy B's future, while the spec says "returns `CommandError::InPast` (unchanged)".
  - The same applies to `UnknownLink`. Taken literally, the ward's ordering ("first drops … then schedules") would truncate before `World::schedule` rejects the link.
- **The edit point 1200 is a snapshot tick**, so the off-grid case is not covered. That case is an edit at, say, 1250, where `seek(1260)` must restore 1200 and replay with the *new* log.
- **Fix** (verified: `p12_extended` and `p12_off_grid` pass the correct implementation and catch all three mutants):
  ```rust
  tl.seek(1200).unwrap();
  let before = (tl.head_tick(), tl.snapshot_ticks(), tl.world().command_log().to_vec());
  assert_eq!(tl.schedule(close(main[1], 1199)), Err(CommandError::InPast));
  assert!(matches!(tl.schedule(close(LinkId(u32::MAX), 1300)), Err(CommandError::UnknownLink(_))));
  assert_eq!((tl.head_tick(), tl.snapshot_ticks(), tl.world().command_log().to_vec()), before,
             "a rejected command below the head changes nothing");
  tl.schedule(close(north[0], 1200)).unwrap();
  // … existing assertions and the 1201..=2400 loop …
  let want: Vec<u64> = (0..=20).map(|k| k * SNAPSHOT_INTERVAL_TICKS).collect();
  assert_eq!(tl.snapshot_ticks(), want, "snapshots resume after the edit");
  for t in [1800u64, 1201, 700, 1200, 2400, 1500] {
      tl.seek(t).unwrap();
      assert_eq!(observe(tl.world()), r[t as usize], "seek({t}) after the edit");
  }
  ```
  Also add an off-grid variant:
  - From the same pre-edit run, `seek(1250)`, then `schedule(close(north[0], 1300))`.
  - Assert head = 1250 and that the last snapshot is 1200.
  - Step to 2400 against the reference `[close(main[0],600), close(north[0],1300)]`.
  - Seek to {1260, 1250, 1300, 1301, 2000, 2400} and compare each with the reference.

### M2. Spec gaps the tests now depend on (`ward-001.md` § Specification; `timeline.md` § T1)
- **Which command log a restore uses.** T1 lists "the full `command_log`" as part of a `Snapshot`, while the ward says restore "keeps the full `command_log`". After an edit, only the timeline's *current* log is correct.
  - State that restore takes the current log, and either drop the log from `Snapshot` or state that it is not used.
- **Where the logs come from on a forward seek.** "Truncates the logs to `s`'s lengths" cannot work for `seek(600)` → `seek(3000)` (test 11), because the position world no longer holds them.
  - State that the timeline keeps the head's logs (append-only, excluded from `snapshot_bytes`), that a restore copies their prefix, and that an edit truncates them at the position.
- **Validation order in `schedule`.** Validate first (`InPast`, `UnknownLink`); only an accepted command at `position < head` cuts the future.

### M3. No snapshot in the suite holds NoRoute or stranded vehicles (`timeline_001_snapshots.rs:197-219`)
- Brief § Verification lists unreachable destinations, and the closure semantics ("wait and retry on a bounded schedule") live in `retries` / `next_retry_tick` / `stranded`.
- Measured (`probe5`): tests 1 and 5 have **no** NoRoute or stranded vehicle at any snapshot tick, and `retries_total = 0` over the whole run.
- **Fix:** add this to test 5, or as a new debug-run test. In three_bridges, close all six bridge links (north, central and south, both directions) at 500 and reopen them at 1100.
  - Measured: NoRoute is 30 → 207 and stranded is 74 at snapshot ticks 600–1080, with `retries_total = 1889`.
  - Assert the precondition `m.no_route > 0 && m.stranded > 0` at tick 600 in the reference.
  - Then `seek(700)`, `seek(1150)` and `seek(1500)` must equal the reference by `observe`, and so must every hash while replaying to 2400.
